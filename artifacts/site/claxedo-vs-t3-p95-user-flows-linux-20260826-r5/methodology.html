Methodology

How this comparison was measured

Agent App Benchmark measures what a coding-agent desktop app actually feels like to use, on real packaged builds, over identical pinned session data, on one machine, in a mirrored order. Every number on the results page comes from the procedure described below.

← Back to results

The premise

Same work, same machine, mirrored order

Real packaged builds

Each application is exercised through its own registered production path as a packaged desktop build — not a dev server, not a stripped harness. Whatever the shipping app does on launch, it does here.

Identical pinned data

Both applications replay the same frozen corpus of completed OpenCode-format sessions. Nothing is generated live, so neither app can win or lose on model speed, network latency, or tool execution.

One machine, mirrored order

Every paired scenario runs on the same host in a balanced mirrored schedule, so warm-up, thermal drift, and ordering effects fall on both applications equally.

Nothing scored as zero

Where a product contract genuinely does not support a flow, the observation is excluded and the driver's exact reason is printed. An unsupported capability is never silently recorded as instant.

The flows

What each measurement actually times

Every flow measures a real user action end to end: from the trusted input event to the moment the requested surface is correct, painted, and ready for the next input.

Session switching

Click a different completed session in the session list, and time until that session's transcript is correctly painted and the app accepts input again. Measured both within one workspace and across workspaces, and both for surfaces never rendered before (cold) and surfaces already rendered once in the same launch (warm).

Why it matters. This is the single most repeated action in a coding-agent app. If it degrades as transcripts grow, the app gets slower the more you actually use it.

Application start

Time from process spawn to a painted, input-ready window. Cold start begins with no saved application state; initialized start begins with application state already on disk.

Why it matters. Launch cost is paid every session and is the first impression of whether an app feels heavy.

Session navigation

First visit times a session surface that has never been mounted. Return times revisiting a session already rendered, with the workspace panel closed. Panel-open returns are isolated as their own seeded-load trend.

Why it matters. The gap between first visit and return shows whether an application is genuinely caching rendered work or rebuilding it every time.

Workspace panel

Every panel interaction is scored on two questions: how quickly the requested surface responded or became usable, and whether rendering stayed inside the 16.67 ms frame budget. Load profiles vary retained directory and file-tab state against the same complete 24-file Review model.

Why it matters. Panel work is where a desktop app either holds 60 Hz or visibly stutters, and frame health is not visible in a latency number alone.

Fairness ledger

What stops this from being a rigged demo

Order control
Balanced mirrored schedule across every paired scenario, so neither application is systematically favoured by running first or last.
Corpus and cases
Compatibility validation requires identical framework revision, scenario, corpus, profile, repetition count, and host identity. Anything that fails to match is reported as unpaired instead of being compared anyway.
Materialization
Each application uses its registered production path. Native and translated mappings are disclosed; unsupported product contracts are not scored as zero.
Presentation vs speed
Deliberate animation duration is never used to name a latency winner. Panel open and close are scored on trusted-input response and p95 frame health only.
Withheld values
A measurement that lost its process family, recorded no sample, or failed validation stays Invalid with its reason attached. It is never substituted with a zero or an average.

Statistics

Why p95, and what the disclosures mean

Every distributional comparison reports nearest-rank p95 with its valid / attempted counts. This run schedules 5 repetitions. Nearest-rank p95 selects the ceil(0.95 × n)-th ordered valid observation, so wherever a value has fewer than 20 valid observations its p95 is exactly the sampled maximum of those observations. Such values are marked "p95 = sampled max"; they remain p95 and are never relabelled as p50. Average, maximum, and p50 stay available as diagnostic drill-down only.

Primary statistic
p95 (nearest-rank)
Why p95 rather than the average
An average hides the slow interactions that actually make an application feel bad. p95 describes the experience you notice — the worst one in twenty actions — which is where sluggishness is felt.
"p95 = sampled max"
Nearest-rank p95 selects the ceil(0.95 × n)-th ordered valid observation. Below 20 valid observations that rank is the last one, so the p95 is exactly the largest observation. Those values are labelled rather than quietly relabelled as a different statistic.
Sampled maximum
Where a sampled maximum appears in the resource tables it is the largest observed framework sample and is diagnostic only; it is not an operating-system true peak.
Winner definition
Lower is better on every metric in this benchmark. A winner is the strict minimum; exact equality is reported as a tie; ratios are quoted against the best remaining value.
